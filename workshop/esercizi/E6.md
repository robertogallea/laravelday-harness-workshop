# E6 — Post-edit: feedback immediato

**Blocco:** B3 · **Durata:** 15' · **Livello MVH:** L5 (verifica e feedback)
**Ingresso:** `cp-05` · **Uscita:** `cp-06`
**Comprimibile:** se la giornata è in ritardo il docente pubblica subito `cp-06` e mostra 3' di feedback al proiettore (taglio 4). In quel caso: `php workshop/bin/checkpoint prendi E6`.

## Obiettivo

Senza post-edit, un errore di tipo l'agente lo scopre allo stop, quando ci ha già costruito sopra altre modifiche. Con il post-edit lo scopre nella tool call successiva. Dopo ogni scrittura `.harness/bin/post-edit` lancia Pint e PHPStan sul solo file toccato, e l'esito torna all'agente come contesto (`additionalContext`), mentre sta ancora ragionando su quel file.

Il post-edit **non blocca**: informa, e fallisce aperto. Il "fatto" lo decide lo stop.

## Da dove parti

- `.harness/rules/post-edit.php`: la policy, con due funzioni che oggi restituiscono `[]` e `null`. Il commento in cima descrive `$results`, come la sezione qui sotto.
- `.harness/bin/post-edit`: l'impianto, già scritto. Legge il payload di Claude o di Codex, lancia i comandi con un timeout, riconosce uno strumento che manca, scrive il trace, non blocca mai.
- `.harness/fixtures/post-edit/`: 9 payload veri di Claude e di Codex. Quelli con `_files` mettono un file campione in `app/`, `database/` o `tests/` per la durata del replay, poi lo tolgono: Pint e PHPStan girano davvero.
- `phpstan.neon`: Larastan al livello 5, su `app/`, `database/` e `tests/`.

## Cosa c'è in `$results`

`feedback()` riceve un elemento per ogni comando di ogni file, non uno per file. Una Write su un `.php` ne produce 2, prima `pint` e poi `phpstan`; una patch su 3 file ne produce 6; al massimo sono 10. Se nessun file ha comandi (Markdown, Blade), `$results` è vuoto e `feedback()` non viene chiamata.

Ogni elemento ha sempre queste sei chiavi:

| Chiave | Cosa contiene | Cosa ci fai in `feedback()` |
|---|---|---|
| `path` | Il file scritto, relativo alla root | Lo nomini nel messaggio |
| `tool` | `'pint'` o `'phpstan'`: la chiave che hai usato in `commandsFor()` | Distingui chi ha parlato |
| `exit` | L'exit code; `null` se il comando non è partito o è andato in timeout | Su `phpstan`, `0` vuol dire pulito |
| `skipped` | `null` se il comando è finito; altrimenti `'missing'` (manca `vendor/bin/…`) o `'timeout'` | Se non è `null`, salti l'elemento |
| `changed` | `true` se dopo il comando il file è diverso | Su `pint`, l'agente deve rileggere il file |
| `output` | stdout + stderr, con i path relativi alla root; `''` se il comando non è partito | Su `phpstan`, ci cerchi gli errori |

Una Write su `app/Support/E6Centesimi.php` con un errore di tipo, lanciata da terminale:

```php
[
    ['path' => 'app/Support/E6Centesimi.php', 'tool' => 'pint', 'exit' => 0,
     'skipped' => null, 'changed' => false, 'output' => '… PASS … 1 file'],
    ['path' => 'app/Support/E6Centesimi.php', 'tool' => 'phpstan', 'exit' => 1,
     'skipped' => null, 'changed' => false,
     'output' => "app/Support/E6Centesimi.php:11:Method App\Support\E6Centesimi::inEuro() should return int but returns string.\n\nNote: Using configuration file phpstan.neon."],
]
```

Se PHPStan non è installato, il secondo elemento diventa:

```php
['path' => 'app/Support/E6Centesimi.php', 'tool' => 'phpstan', 'exit' => null,
 'skipped' => 'missing', 'changed' => false, 'output' => '']
```

Quattro cose che dalla tabella non si vedono:

- **Pint che riformatta esce con `0`.** A dirlo è `changed`, non `exit`. Il suo `output` non serve.
- **L'`output` di PHPStan non contiene solo gli errori.** `Note: Using configuration file…` c'è anche con `exit` 0, quindi `output` non vuoto non vuol dire errori.
- **L'`output` cambia con l'ambiente.** Dentro un agente (Claude Code, Codex) ogni errore finisce con ` [identifier=return.type]` e in coda c'è un blocco di istruzioni; da terminale no. Prendi solo le righe `file:riga:messaggio`, con l'identifier facoltativo.
- **`exit` diverso da 0 non basta a dire che ci sono errori.** Con una config assente PHPStan esce con 1 e non stampa nessuna riga `file:riga:messaggio`: non è riuscito a partire, e lo dirà lo stop.

Per vederlo sulla tua macchina, metti per un momento `return var_export($results, true);` come prima riga di `feedback()` e lancia una fixture con `--verbose`, il comando è qui sotto. Il replay stamperà l'array al posto del contesto, e la fixture può risultare FAIL: toglila prima di andare avanti.

## Cosa fare

1. **TODO 1 `commandsFor($path, $tools)`**: quali comandi lanciare su un file appena scritto.
   - Solo i `.php` sotto `app/`, `database/` e `tests/`, gli stessi path di `phpstan.neon`. Attenzione: `resources/views/welcome.blade.php` finisce in `.php`.
   - Prima `'pint'`, poi `'phpstan'`, entrambi sul solo `$path`: `[...$tools['pint'], $path]`. Usa `$tools` (i comandi di `config.php`), non un `vendor/bin/…` scritto a mano: sul tuo progetto i comandi saranno altri.
   - Perché prima Pint? Pensa alle righe che PHPStan cita.
2. **TODO 2 `feedback($results)`**: cosa dire all'agente.
   - `null` se è tutto pulito: ogni riga in più costa token e attenzione.
   - Se Pint ha riformattato il file (`changed`), l'agente lo deve **rileggere** prima di modificarlo: il suo `old_string` (Claude) o il contesto della patch (Codex) potrebbe non combaciare più.
   - Se PHPStan ha trovato errori: i primi 10 della tool call, ciascuno con il file, la riga e il messaggio. Una riga di errore in `output` è `app/X.php:34:Messaggio.`, a volte seguita da ` [identifier=…]`.
   - Uno strumento che non è partito (`skipped`) non è un problema dell'agente: taci.
   - Al massimo 1500 caratteri. L'impianto taglia comunque, ma perde la coda, e il replay lo conta come FAIL.

Una fixture alla volta, con il contesto che riceverebbe l'agente:

```bash
php .harness/bin/replay --hook=post-edit --verbose .harness/fixtures/post-edit/claude-write-type-error.json
```

## Verifica

```bash
php .harness/bin/verify E6
```

Rigioca le 9 fixture sulla tua policy e, per ogni caso fallito, dice cosa non torna (quanti comandi, il contesto che manca o che è di troppo) e perché la fixture esiste. Si parte da 2/9: Markdown e Blade sono già verdi, perché oggi non parte nessun comando. Da guardare:

- `claude-write-type-error` e `codex-patch-seeder-type-error`: l'errore di tipo arriva all'agente con il messaggio di PHPStan;
- `claude-write-phpstan-missing`: PHPStan non c'è. Il post-edit esce con 0 e non dice niente;
- `claude-write-pest-test`: anche un test Pest si controlla, senza falsi allarmi.

Il confronto con il docente, quando esce `cp-06`:

```bash
git diff cp-06 -- .harness/rules/post-edit.php
```

## Facoltativo con l'agente (3')

Chiedi all'agente di aggiungere a una classe di `app/` un metodo che restituisce un `int` e di farlo tornare con `number_format(…)`. Nel trace (`.harness/runs/<run>/trace.jsonl`) l'evento `post_edit.checked` ha `phpstan_errors: 1`, e il messaggio di PHPStan è nel contesto della tool call: guarda se l'agente corregge prima di rispondere. Ricorda che `app/` è dietro il gate del Task Contract: lavora dentro lo scope di T-001 (`app/Actions/Refunds/`).
