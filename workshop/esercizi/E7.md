# E7 — Change Receipt: dimostrare, non dichiarare

**Blocco:** B3 · **Durata:** 20' · **Livello MVH:** L5 (verifica e feedback)
**Ingresso:** `cp-06` · **Uscita:** `cp-07`, poi la run 2
**Comprimibile:** solo in emergenza (taglio 4 della scaletta): il docente pubblica `cp-07` e si legge il receipt della run di riferimento 2. In quel caso: `php workshop/bin/checkpoint prendi E7`.

## Obiettivo

Alla fine della run 1 l'agente ha scritto "ho finito, passano tutti i test". Era vero: la suite era verde. Ma quali invarianti del contract provavano i suoi test? Nessuna: il contract, l'agente, non lo conosceva.

Il Change Receipt separa ciò che il sistema **dimostra** [D] da ciò che l'agente **dichiara** [A]. Il cuore della parte [D] è una tabella: per ogni invariante del Behavioral Contract, quanti test la provano e con che esito. Un'invariante senza test non è verde: è **non coperta**. Oggi quella tabella dice "Da completare (E7)": la scrivi tu.

La stessa tabella la usa lo stop: un'invariante non coperta o rossa blocca il "fatto" dell'agente nella run 2.

## Da dove parti

- `.harness/rules/receipt.php`: la policy, con una funzione che oggi restituisce `[]`. Il commento dice input, output e le tre regole.
- `.harness/lib/receipt.php`: l'impianto, già scritto. `invariants()` raccoglie gli ID (dai `@contract` delle classi cambiate e dai `--group` dell'evidence di T-001), lancia un `pest --group=<ID>` per ciascuno, conta i test dal JUnit e chiama la tua funzione. `receipt_md()` disegna la tabella, `problems()` trasforma le righe rosse in motivi dello stop.
- `.harness/fixtures/receipt/`: 7 casi, ciascuno con l'input (`contractIds`, `groupResults`), le righe attese (`_expect`) e il perché (`_why`).

## Cosa fare

**TODO `invariantRows($contractIds, $groupResults)`**: una riga `['id' => …, 'tests' => …, 'outcome' => …]` per ogni ID del contract.

1. **Nell'ordine del contract.** `$groupResults` può avere un altro ordine e anche group che non c'entrano (`CANCEL-INV-1`): una riga per ID del contract, nessuna per il resto.
2. **`outcome`** è una di tre stringhe, scritte così: il resto dell'impianto le confronta.
   - `'rossa'` se almeno un test è rosso (`failed > 0`). Anche con `tests` a 0: un `ParseError` rompe il comando prima dei test, e il JUnit dice 0 test e 1 rosso.
   - `'non coperta'` se non c'è nessun test: `tests` a 0, oppure l'ID manca da `$groupResults`.
   - `'verde'` altrimenti.
3. **`tests`** è il numero di test del group (0 se manca): nel receipt è la colonna "Test".

Perché l'ordine conta: un `ParseError` con la regola "0 test → non coperta" valutata per prima direbbe all'agente di scrivere un test che esiste già.

## Verifica

```bash
php .harness/bin/verify E7
```

Rigioca le 7 fixture sulla tua funzione e, per ogni caso fallito, mostra le righe attese e quelle ottenute, con il `_why` della fixture. Si parte da 0/7.

Poi guarda la tabella vera, sulla run 1:

```bash
php .harness/bin/receipt T-001 --of=run-1
```

`--of` applica il diff della run 1 a una copia temporanea del progetto e la verifica con il tuo harness e il tuo T-001 (il working tree non si tocca). La suite dell'agente è verde, ma la sezione "Invarianti → test" ha sei righe ❌ non coperta: è la differenza fra "ho finito" e "posso dimostrarlo". Senza la run 1 (run fallita o saltata): `php workshop/bin/fallback 1`, poi lo stesso comando.

Il confronto con il docente, quando esce `cp-07`:

```bash
git diff cp-07 -- .harness/rules/receipt.php
```

## Indietro?

```bash
php workshop/bin/checkpoint prendi E7
```

Prende il `receipt.php` del docente. Il tuo resta nel commit "wip".

## Dopo: la run 2

L'harness è completo. Prima di lanciare la run 2, il controllo di sala:

```bash
php .harness/bin/verify cp-07          # verde → la run 2 parte dal tuo lavoro
php workshop/bin/checkpoint salta cp-07   # solo se è rosso e non sai come sistemarlo
php workshop/bin/run 2
```

`verify cp-07` controlla anche quello che controlla `run 2` prima di partire: il codice dell'app è quello di `cp-00` (ammessi i docblock `@contract` e i `->group()` dei test), tutto è committato, `progress.md` punta a T-001, e l'agente ha già eseguito gli hook del progetto (l'heartbeat di `doctor --agent`). Alla fine della run 2 il receipt è in `workshop/runs/run-2/receipt.md`, scritto dal tuo `invariantRows`.
